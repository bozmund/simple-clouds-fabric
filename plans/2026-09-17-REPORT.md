- **`createFreshLevel` is the wrong API** — it bakes dimensions against the *vanilla*
  datapack overworld, not the selected preset (see `WorldDimensions#bake` registry
  precedence). The working path: run `WorldLoader.load` to obtain a complete, frozen
  `LayeredRegistryAccess<RegistryLayer>` (worldgen + dimensions + dynamic loaded), look up
  the FLAT preset's generator in `datapackWorldgen()`, build a flat `WorldDimensions.Complete`
  via `new WorldDimensions(...).bake(...)`, and **replace the DIMENSIONS layer** with that
  baked registry (vanilla's `openFresh` relies on `WorldDimensions` holding a
  `replaceOverworldGenerator`-ed complete, which a bare preset does not). Then
  `access.createLevelFromExistingSettings(...)`. With the wrong (bare-preset) dimensions the
  integrated server has no `worldgen/*` registries: `Missing registry
  minecraft:worldgen/world_preset`, and every client chunk packet fails with
  `No value with id -1` in `LinearPalette.read` → the client sees an empty void while the
  server has fully generated flat terrain.
- **`ClientLevel#hasChunk` always returns `true` in 1.20.1.** The 7×7 "chunks loaded" gate
  must test `level.getChunkSource().hasChunk(x,z)` (FULL) — otherwise it passes instantly

### How storms work in the original (file:line, step 2.5)

### Item #1 — VERIFIED: the port never pushes the storm's local rain level

The plan's hypothesis is **confirmed by code** (not assumed):

- **Original** sets the local rain level every frame from the storm, in
  `WorldEffects.renderPost` — `original-1.20.1/.../client/renderer/WorldEffects.java:104-108`:
  `float rainLevel = manager.getRainLevel(camX, camY, camZ); this.mc.level.setRainLevel(rainLevel);`
  (`CloudManager#getRainLevel` is storm-driven: `includesRain`, fade, vertical fade).
- **Port** has the same building blocks — `CloudManager#getRainLevel`
  (`common/world/CloudManager.java:179`), `storminessAtCamera`, `calculateSkyColor`,
  `MixinClientLevel` — but its `WorldEffects` **never calls `setRainLevel`** from them.
  `client/renderer/WorldEffects.java:362` only *reads* the vanilla level
  (`level.getRainLevel(0.0F)`), and `:357-360` force-sets it only under
  `DEBUG_FORCE_WEATHER` (a `false` constant, `:69`).
- The vanilla level's rain is pinned to 0 by `ClientCloudManager`
  (`client/world/ClientCloudManager.java:53-54`, `setRainLevel(0)` / `setThunderLevel(0)`) and
  `ServerCloudManager` (`common/world/ServerCloudManager.java:63`). So the read at
  `WorldEffects.java:362` returns 0, and `:363-367` bails (`rain <= 0.02F`) before spawning any
  drop.

**Consequence (matches the images exactly):** under storms the port shows no custom rain drops,
no vanilla sky darkening (vanilla darkening is driven by the vanilla rain level, which is 0), and
no rain sound. The fix (step 5) is to have the port's `WorldEffects` push
`manager.getRainLevel(...)` to `level.setRainLevel(...)` like the original — a small, localized
change.

## Step 5 — Fix the differences (2026-09-18, in progress)

Order: "breaks the look" first. Starting with the S1/S2/S5 no-rain / no-darkening item.

### Fix 1: local rain level (the "breaks the look" S1/S2/S5 item)

**Root cause (verified step 4):** the port never pushed the storm's local rain level to the
vanilla level, so no rain, no sky darkening, no rain sound.

**Fix (smallest change following the original's logic, adapted to 26.2):**
1. `WorldEffects.tick()` — when the mod owns the weather, push
   `manager.getRainLevel(camX, camY, camZ)` to `level.setRainLevel(...)`. This mirrors the
   1.20.1 original's `WorldEffects.renderPost` (`setRainLevel(manager.getRainLevel(...))`).
   The port's `renderPost` is empty (26.2 removed the old render hooks), so the client-tick
   `tick()` is the equivalent per-frame point.
2. `MixinWeatherEffectRenderer` (new mixin, registered in `simpleclouds.mixins.json`) — cancel
   the 26.2 vanilla rain/snow pass (`WeatherEffectRenderer.render`) when `renderCustomRain` is
   on and the dimension renders Simple Clouds. This is the 26.2 equivalent of the original's
   `MixinLevelRenderer#…renderSnowAndRain` cancel, so the vanilla rain does not double up with
   the mod's custom drops. Only the rain is cancelled; the world border (a separate call in the
   same weather pass) is untouched.

**Result (re-ran the affected scenes; evidence `15-port-storm-rainfix` S1–S5,
`16-port-understorm-rainfix` U-01):**
- **Sky + terrain darkening now works.** The port's S1/S2 went from a bright grey storm to a
  dark storm with a darkened horizon *and* darkened terrain, matching the reference's dark
  look. Before the fix the port's storm was bright; the reference's is dark.
- **Rain level is set** (diagnostic run logged `rain=1.000` under the storm; `resetVanillaWeather`
  only fires on a weather-mode change, so the level persists).
- **Rain sound** is now driven by the rain level (the original's `tickRain` volume scaling is
  vanilla behaviour in 26.2, driven by the level we now set).

**Remaining issues (honest, not yet fixed):**
- **Rain-drop rendering (the main visible gap) — investigated, accepted as a known 26.2
  limitation for this pass.** The reference shows prominent blue falling streaks; the port's 26.2
  `RainDrawPipeline` does not render visible drops. The drops *are* spawned (thousands, `rain=1.0`)
  and the pipeline *is* invoked ("first rain draw" logged), so the level fix is correct. I ran a
  series of in-engine diagnostics (solid-colour fragment shader, then forced the vertex shader to
  known positions, re-running UNDERSTORM each time):
  - Forcing `gl_Position` to a fixed clip-space quad → **renders** (magenta quad at screen centre).
    So the pipeline, render pass, vertex/index buffers, bind group and depth test all work, and the
    pass is correctly drawn to the main target at the `LevelRenderer.render` TAIL hook.
  - Forcing the drops to a fixed *world* position (e.g. 9 blocks above the camera) and transforming
    with `ProjMat * ModelViewMat` → **does not render**. So the `ModelViewMat`/`ProjMat` reaching
    the rain shader do not produce a valid on-screen transform, even though the cloud pipeline
    (same `MATRICES_FOG_SNIPPET`, same `ownTransforms.writeTransform` + `setUniform(
    "DynamicTransforms", …)` + `bindDefaultUniforms`) renders in the correct world position.
  - I also switched the rain pass from the shared per-frame `DynamicUniforms` to its own
    (matching the cloud pipeline's `ownTransforms`, which the clouds use because "vanilla resets
    its shared DynamicUniforms once per frame" at the TAIL hook); the drops still did not render, so
    that was not the (sole) cause. `rain.vsh` itself is correct (camera-right/up = rows 0/1 of the
    column-major view matrix).
  Net: the 26.2 world→clip matrices are not valid for this particular TAIL-hook pass the way they
  are for the cloud passes — a deep 26.2 rendering-internal issue that needs more time than this
  pass allows. The rain *level/darkening/sound* (the step-5 root cause) is fixed; the rain *drops*
  remain a known limitation.
- **Darkening distribution.** The port's storm now also rains/darkens at the *cell centre*
  (U-01 went dark), but the reference's U-01 (directly under the centre, looking up) is **bright**
  (textured grey base, green ground, no rain). So the port's storm has a wider rain area than the
  reference's. This is a **storm-configuration difference** (part of the step 4 cloud-layer /
  storm-shape item), not a bug in the rain-level fix — the fix correctly applies the *local* rain
  level; the port's storm simply has rain where the reference's does not.
