# GPU generation spike (Jan chose option A, 2026-09-12)

## Why
The original mod builds the cloud meshes on the GPU with compute shaders
(`cube_mesh.comp`, `cloud_regions.comp`) over large regions. On 2026-09-10 you
replaced that with `CpuCloudGenerator` because 26.2's Blaze3D API
(`RenderPass`, `CommandEncoder`, `GpuDevice`) has no compute dispatch and no
storage buffers. But the original never used Minecraft's API for compute: it
called OpenGL directly through LWJGL, and 26.2 still runs the OpenGL backend
(both the dev client and Jan's real profile log "Using graphics backend OpenGL",
Mesa, 4.6 core). The CPU generator only covers a small band around the player
and rebuilds it whenever the player moves 2 blocks, so it cannot reach the
original's range or look. Jan wants to find out quickly whether the original GPU
path can run on 26.2.

## Before you start
1. Get the current work to compile, then checkpoint it:
   `git add -A && git commit -m "checkpoint: cloud types load; region wiring in progress"`
   (Jan authorizes this one checkpoint commit although region wiring is not verified yet.)
2. Do NOT delete `CpuCloudGenerator`. It stays as the fallback (Vulkan backend, or if the spike fails).

## The spike -- time-box: stop after about 3 hours of work or 3 failed approaches, whichever comes first
Goal: one real cloud region generated by the ORIGINAL `cube_mesh.comp` on the GPU,
drawn by the existing `CloudsDrawPipeline`, visible in the dev client.

Suggested route (check every API with javap before using it):
1. Only on the OpenGL backend: check that `RenderSystem.getDevice()` is a
   `com.mojang.blaze3d.opengl.GlDevice`; otherwise keep the CPU path.
2. Compile `cube_mesh.comp` and the includes it needs (psrdnoise etc.) from the
   original sources in `/tmp/simple-clouds-src/src/main/resources/assets/simpleclouds/shaders/`
   with LWJGL `GL43` directly (`glCreateShader(GL_COMPUTE_SHADER)`, `glCreateProgram`,
   link, check the info log). Substitute `${LOCAL_SIZE_X/Y/Z}` the way the original
   `client/shader/compute/ComputeShader.java` does.
3. Let the compute shader write straight into a Blaze3D buffer: create the instance
   buffer with `device.createBuffer(..., GpuBuffer.USAGE_VERTEX, size)`, cast it to
   `com.mojang.blaze3d.opengl.GlBuffer` and use its public `handle()` with
   `glBindBufferBase(GL_SHADER_STORAGE_BUFFER, binding, handle)`. Change the shader's
   `SideInfo` output to the 24-byte per-instance layout `CloudsDrawPipeline` already
   uses, so drawing needs no changes. For the face counter (`totalSides`) use a small
   SSBO and read back that one uint after the dispatch (only when regenerating) to get
   the instance count.
4. Dispatch with `glDispatchCompute`, then
   `glMemoryBarrier(GL_VERTEX_ATTRIB_ARRAY_BARRIER_BIT | GL_SHADER_STORAGE_BARRIER_BIT)`.
5. GL state safety: 26.2 caches GL state in `com.mojang.blaze3d.opengl.GlStateManager`
   (`_glUseProgram`, `_glBindBuffer`, `_glBindVertexArray`). After your raw calls,
   restore what you changed through GlStateManager (for example `_glUseProgram(0)`),
   unbind your SSBO bindings, and check `glGetError()` after each step (log an error once).
6. Feed it the real data (noise layers, layer groupings, region transforms) -- the data
   path you are already wiring for the CPU generator.

## What counts as success (measure it, do not claim it)
- `./dev-relaunch.sh` PASS with no GL errors in the log, and the devshot shows voxel
  clouds with visible cube structure, not one flat slab.
- The same seed and position through the CPU and GPU paths give the same shape
  (compare the two devshots).
- Timings: GPU generation (dispatch + readback) against `CpuCloudGenerator` for the same
  area, and the largest area the GPU path generates in under 5 ms.
- Jan's modpack still starts on the real profile (OpenGL backend) without a crash.
